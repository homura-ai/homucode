# Changes from T3 Code

Everything HomuCode changes compared to upstream [T3 Code](https://github.com/pingdotgg/t3code). The [README](./README.md#changes-compared-to-t3-code) has a short summary.

- **Unavailable chat models.** Web and desktop keep a missing model visible and ask you to choose an available model before sending.

- **Linux desktop updates.** The AppImage update feed points to a verified Linux build. If you installed `homucode-v0.0.0-rc.1`, download the [latest Linux AppImage](https://github.com/homura-ai/homucode/releases/latest) and replace your existing AppImage once to get automatic updates.

- **HomuCode branding.** The web, desktop, and mobile apps use HomuCode as the product name and Homu as its short form. Headers render HomuCode as a single line of text with Homu emphasized. The app icon is a multicolour 炎 (flame) in place of the T3 mark, on black for production and dark purple for development; nightly keeps its night sky. Timeline actions such as sending to a Homu thread also use the flame icon. Its Inkscape sources are in `assets/brand-marks/`.
- **HomuCode settings pages.** On web and desktop, HomuCode's settings sit under their own HomuCode group above Agents in the Settings sidebar, split into Interface, MadoHomu, Agent behavior and Building Homu pages. Old links and search results open the page each setting moved to.
- **Provider model refresh from the CLI.** `t3 provider refresh [--provider <instanceId>]` refetches status and models through the running server. Codex custom API providers discover their endpoint's model catalog during regular health checks and explicit refreshes, so new models appear in pickers and delegation without editing Codex configuration.

- **Upstream v0.1.11.** Includes upstream fixes and features through the v0.1.11 release, with HomuCode's thread controls, branding, and mobile sheet fixes retained.

- **No document-wide restyles from `:has()`.** The web client no longer uses CSS `:has()` selectors that style something outside the element holding the `:has()` (composer banner surface, chat header status line, details split buttons, PR rows, sidebar folders and update pill, input groups, dialogs and the Lavender theme palette). In Chromium each DOM change made them restyle the whole page, which made resizing, typing, scrolling and hover lag in large threads. The components now set data attributes from state they already know.

## Server speed

- **Longer T3 Connect passes (off by default).** HomuCode can keep T3 Connect devices signed in for 30 days instead of one hour, avoiding a cloud round trip on most launches. Turn on **Stay signed in for 30 days** beside device approval in Settings → Sharing & access. Removing a device from the T3 Connect account no longer cuts off its existing pass within the hour; revoke it from **T3 Connect devices** on the host instead. Direct pairing keeps its existing lifetime.

- **Agent memory controls on Linux (off by default).** When turned on, each Claude or Codex agent has a configurable memory cap, under the existing cap for all agents. Admission reserves at least 1 GiB per agent and 10% above current use, capped at the agent limit. Starts wait in order when the reservations fill the group budget, show "Waiting for memory", and resume automatically, including after a server restart. Codex uses a separate session per thread while this is on. Configure or disable `agentMemory` in `settings.json`; see [Agent memory controls](./docs/user/background-service.md#agent-memory-controls).
- **Migration checks without a write lock.** In upstream T3 Code, every `t3` CLI command ran the database migration step inside a write-locked transaction on the live database, even when there was nothing to migrate. Each CLI call competed with the server's own writes and could wait up to SQLite's 5-second busy timeout. HomuCode first checks the recorded migration history with a plain read and skips the locked step when the schema is already current, so CLI calls no longer hold up, or wait on, the server.
- **Cheaper work-assistance activity reads.** Work assistance (a HomuCode feature, see [Known limits](#known-limits)) re-reads thread activity as thread events arrive, for every thread it covers on each provider-session event. That query re-parsed every provider thread's stored JSON for each attached row; with one shared Codex session holding about 400 threads, a read took about 400 ms and kept the server's event loop near 94% busy. It now extracts each fork parent once (about 34 ms per read on the same data), and reads activity once per batch of events instead of once per event. In streaming bursts the per-event reads had used about 39% of the event loop.
- **Background Git can be switched off.** Turn off Settings → Threads → Extra features → Background Git (`backgroundGitEnabled`, on by default) to stop the Git work it does on its own: automatic Git status and branch subscriptions, fetch and auto-pull, pull-request discovery, sync, watches and auto-settlement, new turn checkpoints, and automatic worktree cleanup. Restart to apply; Settings shows the running value and any pending change. `T3CODE_BACKGROUND_GIT` overrides the saved choice when set (`0` disables it). While it is off, new turns have no checkpoint diff or undo and the branch and Changes displays don't update by themselves, but explicit Git actions, status refresh from the Git action menu, PR linking, manual cleanup and worktree creation still work. See [Disable background Git](./docs/user/source-control.md#disable-background-git).
- **Git config cache.** `git config` reads are cached for one second, and identical reads in flight are shared, which cuts repeated Git calls from status and pull-request lookups. Callers that need a fresh value skip the cache, a fresh read drops the whole cache, and background and foreground reads are cached separately.

## Threads and subagents

- **Codex model cooldowns.** When CLIProxyAPI reports that the selected model is cooling down on every available account, web and desktop can queue the message and show the remaining wait. The server starts it automatically when the cooldown expires.

- **Provider switch context.** The handoff names the source run’s model and the destination run’s selected model. When the source provider reports which model ran, the handoff uses that identifier.

- **Claude context after Resume.** Stopping a resumed Claude turn before it answers preserves the conversation for the next turn.

- **Full access command approvals.** Codex and Claude threads, including delegated threads, no longer pause for native tool approvals in Full access. If a provider still requires confirmation for a command, HomuCode refuses it automatically and gives the agent the reason.

- **Subagents and moves.** Pinned subagents get their own row in the sidebar's pinned group, naming their parent. New subagents start unpinned by default. Turn on **Settings → HomuCode → Agent behavior → Subagents → Subagents inherit parent pin** to pin new subagents on the same server wherever their parent is pinned. Threads can be moved under another thread or to the root (`thread.move`, the `t3_thread_organize` tool, and the thread menus), with guards so no pending result or wait is lost.
- **Move or copy to another device.** "Move to project" in the thread menus also lists the projects on every other connected device you can operate, and "Copy to project" puts a copy in any project on this device or another one. The conversation (your messages and the agent's replies, not tool activity, attachments or the worktree) is rebuilt there and handed to the agent on the first turn; it uses the thread's model if that provider is there, else that device's default. A move then archives the original, which Undo brings back, so it can't run while the thread is working; a copy leaves the original alone. Web and desktop only.
- **Sidebar folders.** Thread folders sync between desktop, web, and mobile for each connected environment. A folder created from empty sidebar space now uses the selected project’s environment when that scope covers one environment, or the open thread’s environment when browsing across environments. On mobile, long-press a thread to create a folder or move the thread between folders.
- **Sidebar search filters and sorting.** While the sidebar's search box is in use, Filter and Sort take the place of the project filter and the New project and New thread buttons. Filter narrows results by project, status (working, needs you, failed, unread), shelf, last activity, provider, server, pull request or worktree, and can leave message text out of the search; filters alone list the matching threads, and stay set while you open them one by one. Sort orders results by recent activity (the default, where upstream ranks by match), best match, recently opened, newest or oldest, least recent activity, title or project. Web and desktop.
- **Stop.** Stop stops only the current thread by default; Settings → Threads → Extra features can make it stop the thread's subagents too (`stopThreadSubagents`). Shift-click, the background-work Stop or `/stopall` also stops its subagents.
- **Who stopped a run.** Interrupt notices say whether a human (the app's Stop), an agent (MCP tools) or an unknown sender (the `t3` CLI, or a client that names no surface) stopped the run, also when it was stopped before its provider started. A stopped delegated task's result, in its parent's notice and `task_status`, starts with the same reason, so a parent can tell a person's Stop from a failure.
- **Settle a working thread.** Settling a thread while its agent is still working keeps it with your active work until the turn ends, then files it under Settled. Un-settle it before then to keep it. Upstream settled it at once, hiding work that was still running. Web and mobile.
- **Ask again after a restart.** Opt in under Settings → Threads → Extra features (`reaskPendingRequestsAfterRestart`, off by default). When T3 Code restarts while a thread waits on a command or file approval, a question or a secret, the thread resumes and the agent makes the same request again, so it shows up for you to answer. Upstream left the thread stopped until someone sent a message.
- **Bare "stop" or "wait".** Opt in under Settings → HomuCode → Agent behavior → Extra features (`bareStopWaitEnabled`, off by default): a message that is only "stop" or "wait" stops the running turn and goes first in the queue, instead of waiting behind the work it meant to halt. This works on providers that can't interrupt and restart, such as Claude.
- **Subagents default to T3 delegation.** Agents are told to start subagents through T3 Code's `delegate_task` rather than their provider's own subagent tool. The `preferNativeSubagents` setting (off by default, per project) switches the preference back to native subagents. Running Claude, OpenCode and Pi sessions pick up a change.
- **Current thread ID.** Agents in root and delegated threads can call `t3_thread_id` for their own T3 thread ID. Agent shells with `T3CODE_THREAD_ID` can run `t3 thread id`. MadoHomu includes the ID alongside the title in the agent’s context.
- **Thread titles.** The titler sees the project name, so titles can leave out what it already says (`threadTitleIncludeProjectName`, on by default). An optional title ID (`threadTitleIdPrefix`, off by default) gives each active thread a short ID from its title's first letter, numbered when another thread on the server has it (F, F1, F2). Snoozed threads keep their IDs. Settling a thread adds letters (F1a) to free the number again. Existing duplicate IDs are reassigned when the server starts. Both settings are per project, next to the title instructions.
- **Who sent each message.** Every message an agent receives ends with a `[T3]` line naming its source: `[T3] Sent from: <device>. A human sent this message.` for a person, or `[T3] Automatic message from <sender>. No human sent this message.` for scheduled tasks, other agents, `t3 thread send`, subagent and background results, pull request watches and T3 Code's own messages such as the resume after a restart. Turn on **Show message sender labels** in Settings → HomuCode → Interface → Sent messages to show "Human · <device>" or "Automatic · <sender>" above sent and queued messages on this device. The agent line is on by default and can be turned off in Settings → Threads → Extra features (`messageSentFromEnabled`). Name connected devices there too; the state folder's `device-names.json` is still read, with GUI names taking precedence. The phone app keeps its own name (Settings → Threads → Extra features → Phone name, or the setup sheet) and sends it to every server it connects to; a server's own name for that device still wins.
- **`/q`.** Asks one question in the same thread on a "Quick model" (a new setting): the thread switches to the quick model for that one answer, then switches back to its own model. Context and prompt cache are kept: on the same provider the answer runs in the thread's own provider conversation, so nothing is handed off. On another provider the quick model gets a summary of the thread, and the switch back resumes the thread's original provider conversation with only the missed turn added. Picking a Quick model across environments replaces the previous model and its options on each environment.
- **`/cd`.** `/cd <folder>` moves the thread to that folder's project and adds the project if there isn't one yet. A relative folder starts from the thread's current one, and `~` works. The thread menu's **Move to project** does the same for projects on the current machine. Files switches to the new folder, and the provider resumes the idle thread's conversation there on its next turn. In a new thread that hasn't started, `/cd` opens a new thread in that project instead. Web and desktop only.
- **Machine for threads without a project.** Settings → Connections → Threads without a project picks which machine those threads start on, per device. Automatic keeps upstream's order: this device's own machine, then the one on screen.
- **Snooze menu.** On web and desktop, right-click a snoozed thread and choose Snooze to change its wake time. Custom… comes first in every snooze menu, above the presets (web, desktop and mobile). Settings → Threads → Snooze options holds up to 16 options instead of 8, and an option can wake a number of days from today at a set time ("Days ahead", up to 30 days), shown as "In 4 days" with its weekday, plus the date when it is a week or more away.
- **Agents reach the rest of the thread menu and Settings.** Agents get the app's remaining safe actions through T3's MCP tools. In `t3_thread_organize`: mark read, reorder a pin, turn auto-settle off or on, restart the provider session, and close a guest share. In `t3_queue`: start a queued message now or resume a paused queue. In `t3_pending_request`: dismiss a question. In `t3_environment_preferences_update`: an allowlist of Settings that excludes secrets, sign-ins, spending, notifications, data deletion and agent permissions. New tools import Claude Code and Codex sessions, read a thread's checkpoint diff, edit keyboard shortcuts, read usage, turn a scratch thread into a project, and cancel or retry worktree setup. Importing sessions, creating a project from a thread, and editing shortcuts ask for approval below Full access, and shortcuts can bind only built-in commands. The `t3` CLI adds `t3 thread organize` (including move-project) and `t3 pending-request dismiss`. Deleting threads, restoring checkpoints, sign-ins, secrets, public sharing, updates and restarts stay human-only.
- **Approve project and environment changes.** Below Full access, a thread that adds, updates, clones or deletes a project, links or unlinks an environment, changes environment preferences or the theme, or runs a scheduled task now gets an approval prompt instead of a refusal. Approve runs the call; decline leaves everything as it was. Full-access threads are not asked, and calls forwarded to a linked environment are still refused there.
- **Autoreviewers.** An `autoreview` tool attaches reviewer subagents to a thread. They read its activity in batches and send back findings, which steer into the running turn or wait in one queued message. Options cover batch size, pacing, waking on each tool call or each user message, and a custom preamble. Findings that arrive after a Stop wait for the user's next turn. They are off by default: turn on Settings → Threads → Autoreviewers (`autoreviewEnabled`). While it is off the tool refuses to add reviewers, and reviewers already attached pause until it is back on. Using them isn't recommended: Settings labels them that way, and setup doesn't offer them. They often get in the way of other threads because they lag behind: if the main thread keeps working, the reviewer gets no new context until it replies, and that reply is based only on old context. Other times a reviewer gets stuck replying LGTM over and over.
- **Opt-in Claude background command holds.** Turn on **Settings → Threads → Keep Claude threads working while background commands run** to keep a Claude thread in Working (shown as Waiting) from the moment a background command starts until it ends. This is off by default and applies to new background tasks without a restart. The agent can release a command it leaves running, such as a dev server, with `t3_background_wait` and `waiting=false`; otherwise it holds until the command exits or reaches its background timeout. Claude monitors keep their upstream held behavior.

## MadoHomu

- **MadoHomu.** An opt-in view locked to one project, on web, desktop and mobile, modelled on Claude Duet. It is one thread list in sections: Pinned, your own sections, Working, Scratch, Snoozed and Settled. Threads made in MadoHomu are pinned across devices, independently of sidebar pins, and can be reordered by dragging and filed under sections you add; every other thread in the project sits in Scratch, and dragging one onto Pinned pins it. A Scratch thread that is working shows in a Working section, at the top of Scratch or in place, as "Working threads" in MadoHomu settings says; pinned threads never move. Every section folds, Scratch shows its first 10 threads with Show more, and a thread that needs approval or input always stays in view, with a count on a folded section. Rows show when a thread is working or needs approval, input or a guest's answer, and the thread menu is the normal one plus Edit and Move to, with selection, bulk actions and press-and-sweep settle on web. On web and desktop the thread keyboard shortcuts work in MadoHomu and links to the project's threads stay in it; on mobile the open thread's header menu has Move to and Edit. New thread on a branch from a MadoHomu thread lands in Pinned. Each thread has an editable title, icon, icon colour and short prompt, and the agent sees the title and prompt on every turn without them showing in the chat. MadoHomu's threads stay out of the HomuCode thread list unless "Show MadoHomu threads in HomuCode" is set to Scratch only or All. The project picker can make a new project. MadoHomu threads use the same permission modes as other threads: new ones start in the project's default mode and the composer picker changes it. An optional morning brief runs as a daily scheduled task in plan mode, so it proposes next steps and asks before acting. Turn it on in Settings → HomuCode → MadoHomu. On Android, open it from the navigation rail whenever the rail is visible. On iOS, open it from the thread list. Android hides the thread-list row by default and lets you restore it in MadoHomu settings. See [MadoHomu](./docs/user/madohomu.md).
- **Separate new-thread defaults.** Changing projects, opening threads, and drafting new threads in MadoHomu keep HomuCode’s last-used project as it was.
- **MadoHomu desktop app.** On desktop, MadoHomu opens in its own landscape window (`--madohomu`), which can merge into the main window and split out again. While MadoHomu and its desktop app setting are on, it gets its own launcher: a `.desktop` entry on Linux, a jump-list task on Windows and a dock menu item on macOS. Turning either off removes it. `scripts/install-madohomu.mjs` installs it as MadoHomu.
- **MadoHomu on Android.** Enabling MadoHomu adds its own launcher icon and Recents task. It opens your selected MadoHomu workspace, and Back follows the active task in split screen. Disabling MadoHomu on your last enabled environment removes the icon.

## Feature offers

- **Offers for opt-in features.** Setup offers MadoHomu, quick model, settings sync and the status line on page 1, with HomuTheme preselected in a theme picker on first install. Page 2, "Extra features", offers delegation, Stop and steering behavior, asking again after a restart, message attribution, title options, background Git and building T3 Code. After an update, users are shown a selection page with new features (`featureOffersSeen`); when either list has fewer than three, both share a page. Device naming and optional Building T3 setup follow. Mobile also offers its device-local Faster phone launch, tracking that offer on each phone. Page 2 also offers staying signed in to T3 Connect for 30 days and keeping Claude threads working during background commands. Settings stays the way to change every choice.

- **One setup for several environments.** On the phone, the HomuCode features sheet saves one set of choices to every environment you tick. Each feature shows a colored chip per environment: filled when it supports the feature, struck through when it doesn't, and "(when online)" for an offline environment, which gets the choices when it reconnects. Phone-only choices are always available. When another connected environment has already been set up, its answers are filled in for features this one hasn't offered yet, and the sheet says which environment they came from; web and desktop do the same. Features that are already on, such as MadoHomu and Quick model, can be turned off from setup.

- **Find setup choices in Settings.** Search web and desktop Settings for the options offered during setup. In Settings → HomuCode, you can change T3 Connect’s 30-day sessions, find Building Homu fields by name, and choose or turn off Quick model on mobile.

## Queue and steering

- **Auto and steer delivery.** Messages sent with delivery mode auto or steer are steered in as soon as the turn can take them. `t3 thread send` takes `--mode queue|auto|steer|restart`, and `t3 thread configure` sets permission and interaction modes.
- **Steer now and Send now.** Use **Steer now** on a queued message to send it into the running turn, or **Send now** to stop the running turn and start the next one with that message, on any provider. **Send now** below an unread Claude steer interrupts the current work so the message can be delivered. These actions are available on desktop and mobile.
- **Steer all queued messages.** While a turn runs, Ctrl+Enter (Cmd+Enter on macOS) in an empty composer steers every queued message into the running turn in order, stopping before one that must start its own turn. With a draft, it still sends the draft with the opposite queue or steer action.
- **Idle model changes apply to incoming messages.** Changing an idle thread’s model or provider updates the chat immediately and applies to the next message, including messages sent by other threads. The context handoff runs when the next turn starts.
- **Apply model and effort changes now.** Opt in under Settings → Threads → Extra features (`applyModelChangeNow`, off by default). Changing the model or effort of a thread whose turn is running restarts that turn on the new setting, and the agent carries on with its task without a new message; a notice in the thread says so. It works from web, desktop, mobile, `t3` and agent tools, and for delegated threads, whose parent sees the task still running rather than stopped. Claude effort changes it can apply to the running turn are applied without a restart. The chat timeline marks the model or effort switch on the running or replacement turn where it applies. Codex loses most of its prompt cache when effort changes. Upstream applies the change on the next turn.
- **Resend unread steers after Stop.** On by default; turn it off under Settings → Threads → Extra features (`claudeSteersSurviveStop`). When you steer Claude while it's running a tool, Claude reads your message only after the tool finishes. If you press Stop first, upstream drops the message and you have to send it again. With this on, T3 sends it again for you: it steers the run if one is still going, or starts the next turn.
- **Send while the previous message is still sending.** A message sent before the previous one has gone through waits instead of being refused: it shows as the queued or steering message your follow-up setting makes, marked "Sends once your previous message goes through", and sends itself once the previous one does. Anything you type meanwhile stays in the composer. Web and desktop.

## Composer and messages

- **Apply model picker changes instantly or on close.** On web and desktop, check **Apply instantly** next to the permissions control to apply changes to the running turn, or opt in to applying only the final pick when you close the picker. With both picker options off, the environment's setting still applies.

- **Smoother chat resizing on web and desktop.** Resizing the chat or toggling a panel no longer makes the browser recalculate styles for every timeline row when the chat insets change.

- **Status line.** The top bar shows context tokens, 5-hour and weekly quota with projected remaining markers, thread cost, uptime, cache hits and I/O. Labels shorten before values drop, and the weekly dial stays visible longer than the 5-hour dial. Gauges, reset countdowns and cache hits use green-to-red scales that blend with the theme. Reset countdowns show recent burn risk, with configurable smoothing in the expanded view and Settings. Cost uses recorded main-agent usage for the active provider thread, with subscription estimates for recognized plans and an API price setting. Mobile colors the model name and the short label, such as `hi` or `xhi`, by effort. Desktop and web color the effort in the composer. Hover, focus, or tap for details, including available API time, output style, fast mode, and versions. CLIProxyAPI limits can pool matching accounts, and the weekly depletion ratio is optional. Custom status line commands still receive Claude Code's JSON and render ANSI text. The header clock stays visible with the status line off.
- **Plain-text sent messages.** A setting shows your sent messages as the plain text you typed instead of rendered Markdown. Find in thread matches what is shown.
- **Keep `+` at the start of a line.** A setting keeps a `+` at the start of a line in your sent messages as typed, instead of turning it into a bullet.
- **Answered questions keep their options.** Answered and cancelled questions show every option and its preview, not only the chosen one. Web and mobile.
- **End jumps to the latest message.** Pressing End scrolls the thread to its end and resumes following new output (`thread.scrollToEnd`), from anywhere outside a text field, and from the composer or the find-in-thread box once the caret is already at the end of its text. A second End within half a second of one that did not scroll leaves the thread where it is. A list, menu or other scrolling panel with focus keeps its own End. Web and desktop.

## Desktop, CLI and mobile

- **No stray input on UI that just changed.** A press or key is dropped when it lands within half a second of the UI changing under it without being asked for, so input aimed at what was there before can't act on what replaced it: a control that appeared or slid under the pointer, a dialog or field that took focus, or the first moment after startup. Questions, approvals, feature offers and the settings sync dialog always count as unasked, so a click outside the feature offers can't dismiss them unread, and a fast double-click can't answer two questions. Changes that follow your own press or command key within a second, such as a menu you opened, take input at once, and typing into the field you were already in is never dropped. Upstream closed the question case as not planned ([#31108](https://github.com/pingdotgg/t3code/issues/31108)). Web and desktop; on mobile, taps are held at startup and when a question, approval or feature offer appears, and the feature offers sheet can't be dismissed in that moment.
- **Cached Home opens sooner on Android.** HomuCode builds Home's thread list once all launch caches are ready instead of rebuilding it as each environment arrives. With three environments and about 900 cached threads, this cut cold launch by about 0.3 seconds on an offline Android emulator.
- **Settings sync.** Web, desktop and phone clients keep their own settings (theme and theme library, appearance, chat, diffs, sidebar and the rest of what each device stores) the same across devices, through every server they are connected to, so devices that share any server stay in step and a device connected to several servers carries settings between them. It is opt-in per device; turn it on in Settings → HomuCode → Interface → Settings sync. When a setting changed both on this device and elsewhere since they last synced, and on a device's first sync with a server when its settings differ from that server's, a dialog names the server and asks which value to keep for each setting (showing the whole value on each side, with Read more for long ones), one server at a time while the others keep syncing. "Decide later" pauses sync with that server until the app restarts. Device-specific settings (onboarding, microphones, faster phone launch, where scratch threads start, and the sync switch itself) never sync. The phone app syncs the settings it shares with web and desktop (theme, appearance, language, chat, tool calls, math, model favorites, project grouping and the working shelf) through every connected server, and has its own switch in Settings → HomuCode.
- **Completions and CLI.** A durable local completion sink and native CLI task controls. Launch receipts and the AppImage runtime are reused across CLI calls.
- **Update when agents are idle.** On by default; turn it off per machine under Settings → Threads → Extra features (`autoUpdateWhenIdle`). The desktop app installs a ready update, downloading it first if needed, once that machine's agents have been idle for five minutes and it has had no keyboard or mouse input for five minutes. Each server updates each provider on its own once that provider's agents on that machine have been idle for five minutes. Each version is tried once per start. See [Update automatically when agents are idle](./docs/user/updating.md#update-automatically-when-agents-are-idle).
- **Desktop on Linux.** Thread links reuse the pinned AppImage cache, and URL launches request Wayland activation.
- **Undo a staged build.** On AppImage installs, Building Homu shows (or Settings → HomuCode while that page is hidden) the build the next start loads, with an Undo button that renames that AppImage to `.off` so the one staged before it loads instead. The toast after Undo offers Redo.
- **App scripts.** TypeScript files in `~/.t3/userdata/scripts` that drive the window through a small `t3` API: run any keybinding command, open a thread, open a new-thread composer with a prompt and model, send to a thread, read the current thread and project, and show a notice. Bind one to `user.<name>.run`, or run it with `t3 app run <name|file.ts>`. Three switches in Settings → HomuCode → Interface → App scripts, all off by default and kept on each device (never synced): app scripts at all, running them from a terminal, and accepting `t3 app run` from an agent's shell. No agent tool runs scripts or changes these switches. Desktop and a browser on the same machine; not mobile or a browser over the network. See [App scripts](./docs/user/app-scripts.md).
- **Faster phone launch.** Opt in on the phone in Settings → General (`fasterPhoneLaunch`, off by default). The phone app connects to your T3 Connect machines as soon as it opens, using the account you were last signed in to, instead of waiting for sign-in to load over the network. If sign-in then reports no account or a different one, the app drops the restored account at once.
- **Over-the-air Android updates.** HomuCode's Android builds get updates from HomuCode's own EAS Update project instead of having them switched off, so changes that only touch the app's JavaScript reach installed phones without a new APK. The app checks on launch and applies an update the next time it goes to the background. Builds use a fingerprint of their native code as the runtime version, so an update only reaches APKs it was built for. Upstream's EAS project, owner and slug stay the defaults; the `T3CODE_EAS_*` and `T3CODE_MOBILE_UPDATES_CHANNEL` settings override them.
- **Phone search keeps every keystroke.** Typing in the phone's thread search no longer makes letters vanish and reappear, or drops some of them. Upstream's search box waited for the whole thread list to redraw before showing each letter; HomuCode shows the letter at once and updates the list after.
- **Android undo notice.** The thread undo notice shows at the top of the screen on Android.
- **Find in thread on mobile.** The magnifying glass in a thread's header bar opens a find bar that searches the thread's messages and plans, shows the match count, and steps through matches newest first, scrolling to each one and loading earlier history when needed. Upstream has find in thread on web and desktop only.
- **Faster Android start.** On Android the app starts running about 0.4 seconds sooner at launch. The release app loads each part of its code when it is first used; upstream loads all of it at launch.
- **Faster phone start.** The phone app starts about a second sooner. Upstream ran a language-support check at every launch whose result never changes on the phone; HomuCode skips it.
- **Android opens on the thread list.** A cold start from the launcher icon shows a saved picture of the thread list about half a second in, in place of the app-icon splash. The real list takes its place once it shows the same rows, about four seconds in on the test emulator, and at five seconds at the latest. The picture is saved when the app goes to the background with the list at its top and nothing over it. It is used only while the window size, display size, font size, dark mode, language and installed build are the same, and it is deleted on sign-out, when an environment is removed or its cache is cleared, and when the app's theme, text size, language, tabs, thread grouping or thread list filter change. Until the swap the list does not take taps and can show times and statuses from the last session. Phone layout on Android 10 and later; tablets and unfolded foldables start as before.

## Add-ons

- **Optional tools.** [`addons/`](./addons/README.md) holds two build tools: cloud builds on boat.dev and staged-build loading with rollback. Both are off by default. Enable "Show Building Homu settings" in Settings → HomuCode to configure and run cloud-build and load-build from the app, including checksum verification and automatic rollback on AppImage installs. The page also runs Android APK builds, can serve APKs over the LAN until switched off or the server stops, and sets the AppImage build folder. Setup can open this page too. A T3 Code checkout and a signed-in boat CLI on the server are required for builds.

## Smaller items

- The optional Vite+ wrapper runs heavy checks on Boat. It reuses one warm box, stops it after 15 idle minutes, and runs one low-priority local check at a time during a Boat outage. Android dev-client cache misses also build on Boat.

- Schedule and usage-stop fixes, settle timestamps and agent message timestamps, a human-message timestamp in activity, thread title instructions that override the default length limits, project router creation notices (off by default; see [docs/project-router-notices.md](./docs/project-router-notices.md)), and thread and project pins kept per device.
- **Find in thread from thread details.** The thread details card on web and desktop has a Find in thread row at the top. Hide it from the card's right-click menu or Settings → Appearance → Thread details.
- **HomuTheme.** HomuTheme (formerly Lavender) is the default theme on web, desktop and mobile, and is listed first in Settings, the command palette and the phone app. In dark mode its message bubbles and composer are darker than they were.
- **Theme tweaks keep the rest of the theme.** An agent's `t3_theme_set` and `t3 theme set <file> --base <id>` build a theme on a built-in or published one, so changing a couple of colors keeps the base's other colors, both appearances and its CSS. `t3_theme_read` reports the theme clients show (HomuTheme, id `lavender`, when the server sets none) and can return a built-in theme's file. Before, a theme that set a few colors got a generic palette for every other role and lost the default theme's fonts and CSS.
- **Searchable keybinding commands.** The Command picker for a new keybinding in Settings → Keybindings has a search field. It matches the command's name or its ID, ignoring spaces and punctuation, so "newlocal" and "chat.new" both find Chat: New Local. Arrow keys and Enter pick a result. Web and desktop.
- **Idle compaction without the fallback.** Settings → Providers → Advanced → Compact idle threads splits "Before the cache expires" in two. "Before cache expires, or on return" is upstream's mode: a thread that misses its window is compacted when you return. "Only before cache expires" never compacts on return, so a thread that missed its window sends with its full history (`idleCompactionFallback: false`). A Claude provider's own "Before the cache expires" override follows this choice.
- **Actions for all projects.** Settings → Projects with All projects selected edits the actions every project gets (`defaultProjectScripts`), with their shortcuts, so a `script.<id>.run` shortcut works in any project. Upstream only let you change that list by editing `settings.json`. A project with its own list is marked as overriding it, and reset returns it to the shared list. Web and desktop only.
- **Custom script keybindings.** In Settings → Keybindings, a new keybinding can run a Bash command instead of a built-in command: press **Bash** next to the command list and type it. It runs in a new terminal in the thread's checkout on the thread's machine, in every project, and stays editable in its row. It is stored as `bash:<command>` in `keybindings.json`. Use [`keybindings.json` to bind a TypeScript app script](./docs/user/app-scripts.md#run-a-script-with-a-keybinding). Web and desktop.
- **Sheets centered on wide Android screens.** On tablets and unfolded phones, sheets such as HomuCode features are centered (or centered beside the hinge when the phone is half folded) instead of sticking to the left edge. The fix is in HomuCode's copy of `react-native-screens`.
- **HomuCode features keeps your choices.** On the phone, unfinished choices stay saved for each environment when a connection drops, saving fails, or the sheet is dismissed. Not now offers snooze presets and a custom duration in minutes, hours or days, including across app restarts. Setup names each environment and explains which features need a newer HomuCode server or additional permissions. Phone settings remain available, and build status requests run only on servers that support them. Setup stays closed once all available choices have been saved.
- **Android sheets scroll back up.** In sheets such as HomuCode features, dragging down scrolls the content back to the top before it moves the sheet, instead of pulling the sheet down. Part of the fix is in HomuCode's copy of `react-native-screens`.
- CI runs the Linux jobs on GitHub's hosted runners, which are free for public repos. Setting the repo variable `CI_LINUX_RUNNER` to a runner label (such as `boat-warm`) moves pushes to `main`, the owner's PRs, and PRs labelled `ci:boat` onto that runner instead.

## Known limits

- Work assistance is untested and not recommended. It lets a signed-in local `t3` client start a helper agent on a thread that has been working nonstop for over 5 minutes; HomuCode never starts one by itself. It is off until a project and environment are chosen in Settings → Threads → Work assistance (`workAssistanceTarget`), and setup doesn't offer it. It covers one project on that environment; configure each environment separately.
- The phone and web apps published by upstream (App Store, Google Play, app.t3.codes) don't have these changes. Per-device pins, for example, only fully apply to clients built from this repository.
- The Git config cache has been code reviewed but not yet run as part of a built app.
